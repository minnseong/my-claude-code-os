# Interview 스킬

모호한 요청을 받으면 **구현하지 않는다.**
지침을 최우선으로 확인하고, 작업을 분해한 뒤, 질문으로 요구사항을 확정한다.

---

## Step 1: 컨텍스트 스캔

이미 결정된 것을 파악해 불필요한 질문을 제거한다.

```bash
# 앱 정책 — 최우선 지침
cat {정책_문서} 2>/dev/null

# 기존 도메인 모델
find {소스_루트} -name "*.java" 2>/dev/null | head -30

# API 계약서
cat {문서_루트}/api/endpoints.md 2>/dev/null
```

---

## Step 2: 작업 크기 판단 및 분해

요청이 아래 중 하나에 해당하면 **큰 작업**으로 판단한다:
- 여러 레이어(DB·서비스·컨트롤러·UI)에 걸친 작업
- 정책 변경이 수반되는 작업
- 새로운 도메인 엔티티가 필요한 작업
- 여러 에이전트(기획·백엔드·프론트·QA)가 필요한 작업

**큰 작업이면** 아래 형식으로 분해한 뒤 사용자에게 확인 후 진행한다:

```
📦 작업 분해: [기능명]

Step 1. [선행 작업 — 예: POLICY.md 업데이트]
Step 2. [도메인/DB 설계]
Step 3. [백엔드 구현]
Step 4. [프론트 구현]
Step 5. [QA]

이 순서로 진행할까요? 빼거나 바꿀 단계가 있으면 말씀해 주세요.
```

작은 작업이면 바로 Step 3으로 넘어간다.

---

## Step 3: 지침 충돌 감지

분해된 작업 범위를 기준으로 **CLAUDE.md 또는 POLICY.md와 충돌하는 부분**을 찾는다.
요청 전체가 아니라 **분해된 각 Step 기준으로 비교**하기 때문에 충돌의 심각도를 정확히 판단할 수 있다.

충돌이 발견되면 **구현 전에 즉시 사용자에게 알리고 방향을 묻는다.**

```
⚠️ 지침 충돌 발견

분해된 작업 중: Step N — [작업명]
충돌 지침: [POLICY.md §N 또는 CLAUDE.md 해당 항목]
충돌 내용: [구체적으로 어떤 부분이 충돌하는지]

→ 지침을 변경하고 진행할까요, 아니면 다른 방향으로 접근할까요?
```

충돌이 없으면 Step 4로 넘어간다.

---

## Step 4: 인터뷰 (최대 5라운드)

**AskUserQuestion 도구**로 선택지를 제시한다. 오픈 질문 금지.

### 질문 생성 원칙

요청을 아래 5개 차원으로 분해해 모호한 항목만 질문한다.
이미 POLICY.md·코드에서 답이 나온 항목은 제외한다.

| 차원 | 물어야 할 것 |
|------|------------|
| **범위** | 이번에 만들 것 / 만들지 않을 것의 경계 |
| **기술 방식** | A vs B vs C 중 어떤 방식 |
| **데이터** | 저장할 정보, 필수/선택 여부 |
| **UX 흐름** | 사용자가 어떤 순서로 사용하는지 |
| **제약 조건** | 쓰면 안 되는 것, 지켜야 할 기준 |

### 라운드 운영 규칙

- 한 라운드에 최대 4개 질문 (AskUserQuestion 제한)
- 상위 결정이 하위 결정을 결정한다 — 상위 결정 먼저
- 답에 따라 불필요해진 하위 질문은 건너뛴다
- **최대 5라운드**. 5라운드 후에도 모호한 것은 Claude가 합리적 기본값을 제안하고 확인받는다
- 유사 서비스를 선택지로 활용한다 ("카카오처럼? 토스처럼?")

### 라운드 시작 전 출력 형식

```
📋 요청 분석: [사용자 요청 한 줄 요약]

이미 결정된 것:
- [항목 1]
- [항목 2]

확인이 필요한 것: 총 N가지 (라운드 X/5)
```

---

## Step 5: 요구사항 확정 및 요약

모든 라운드가 끝나면 아래 형식으로 정리해 확인받는다.

```
✅ 확정된 요구사항: [기능명]

범위
- [결정 사항]

기술 방식
- [결정 사항]

데이터
- [결정 사항]

UX 흐름
- [결정 사항]

제약 조건
- [결정 사항]

작업 계획
1. [Step 1]
2. [Step 2]
...

─────────────────────────
이 내용으로 진행할까요?
→ "응" / "맞아" → /plan 또는 해당 에이전트로 연결
→ 수정 요청 → 해당 항목만 다시 질문
```

---

## Step 6: 인터뷰 로그 저장

사용자가 확정하면 아래 경로에 로그를 저장한다.

**경로**: `.claude/interview-logs/YYYY-MM-DD-HH-MM-[기능명].md`

**로그 형식**:

```markdown
---
date: YYYY-MM-DDTHH:MM:SS
request: [원본 요청 그대로]
rounds_used: N
conflicts_found: true/false
task_size: large/small
---

## 원본 요청
[사용자가 입력한 원본 텍스트]

## 지침 충돌
[충돌 없음 / 충돌 내용 기록]

## 작업 분해
[분해 결과 또는 "단순 작업으로 분해 생략"]

## 인터뷰 라운드

### Round 1
**질문**:
- Q1: [질문 내용]
- Q2: [질문 내용]

**답변**:
- A1: [사용자 답변]
- A2: [사용자 답변]

### Round 2
(반복)

## 확정된 요구사항
[Step 5의 요약 내용 그대로]

## 메타 분석 (Claude 자동 작성)
- 가장 모호했던 차원: [범위/기술방식/데이터/UX흐름/제약조건]
- 충돌 발생 지침: [해당 없음 / POLICY.md §N]
- 핵심 결정 포인트: [이 인터뷰에서 가장 중요했던 결정 1~2가지]
- 다음 번 이 유형 요청 시 선제적으로 물어볼 것: [제안]
```

로그 저장 후 사용자에게 경로를 알린다.

---

## 실행 원칙

- **구현하지 않는다.** 이 스킬의 출력은 항상 질문·계획·요약이다.
- **추측하지 않는다.** 모르면 질문한다.
- **지침이 최우선이다.** POLICY.md·CLAUDE.md와 충돌하면 구현 전에 반드시 확인받는다.
- **이미 결정된 건 묻지 않는다.** POLICY.md·기존 코드가 답을 갖고 있을 수 있다.
- **5라운드 초과 금지.** 5라운드 후에는 합리적 기본값을 제안하고 확인받는다.
- **사용자가 확정하기 전까지 다음 단계로 넘어가지 않는다.**
